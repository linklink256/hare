## 原因核对

- 当前保存的设置是开启、40%、保留 1 条，相关模型窗口为 1,000,000。没有修改这些设置；没有历史设置审计，不能只凭当前设置证明过去每个时刻的设置。
- `automaticCompressionEnd` 使用 `maxOf(estimateContextTokens(requestMessages), usageTokens)`。即使模型报告的总上下文很低，全量粗估仍能独立触发。
- 第一轮四条历史粗估 416,110，其中 Reasoning=322,043；不计这些 Reasoning 时为 94,067。加上新用户消息后粗估 416,248，系统提示还会继续增加。
- 第二轮有效前缀粗估 638,748，其中上一轮 assistant 的 Reasoning=474,901；加新用户消息后为 638,829。
- 当前 40% 的正常阈值是 400,000（常规 4,096 回复预留不会把该阈值进一步降低）。两次全量粗估都越过该阈值，真实用量却只有约 10.5% 和 15.0%。可复现的机制是全量启发式粗估覆盖真实 usage，而不是把累计 800,956 直接用作本次上下文。
- 历步思考文本的本地字符估算不等于模型下一次请求真正保留/计入窗口的 token。这里不进一步断言网关一定没有发送或一定丢弃了某类 reasoning；未抓取请求/网关内部状态。

## 修复方向与当前状态

本轮仅核查，未修改压缩策略。建议后续：可靠、同模型同请求的 provider usage 作为已知上下文基线；只估算该基线之后真正新增且会发出的内容（包括同一 assistant 内新执行工具的结果）；没有可靠 usage 才回退全量估算。不要简单忽略所有思考、只调高百分比，或漏算刚新增的大工具输出。

触发记录应另存数值来源、真实 usage、增量估算、预算、模型窗口和压缩前后收益，不记录正文/密钥。旧多步消息的累计 usage 不能冒充单次 usage；无收益重复压缩应单独处理。
