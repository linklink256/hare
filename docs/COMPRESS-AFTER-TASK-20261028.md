# 自动压缩改为本轮任务完成后执行（2026-10-28）

## 用户要求与任务边界

任务执行中达到上下文阈值，不立即压缩；等本轮任务正常完成后再压缩。

- 本轮任务 = `runAgent` 从接收本轮输入/续跑开始，经过全部模型请求与工具调用，最后返回 `AgentFinishReason.Completed`。
- 不是某一步模型请求完成，也不是一次工具结束；不以任务板 pending/done 代替真实运行结果。
- `AwaitingApproval`、`StepLimitReached`、异常和取消都不触发本轮结束后的自动压缩。
- 审批续跑会重新建立本轮上下文并检查阈值，正常完成后才执行维护。

## 实现

1. `ChatRequestFactory.prepareStep` 仍组装真实请求并检查阈值，但只设置本轮 `DeferredTaskCompression.pending`；不调用摘要模型，不插入检查点，不使用中途摘要 overlay。
2. `ChatService` 收齐任务完成事件后，先通过 `finishGeneration` 保存回复，再进入仅限 `Completed` 的后置压缩路径。
3. 后置压缩用本轮原始分支历史 + 最终完成消息重新检查。续写同一条 assistant 时替换旧快照，不能把同 ID 的完整消息重复追加。最后一步输出首次达到阈值也可在此检测。
4. 最终检查已不需要压缩时清掉过期标记；同一轮最多尝试一次维护。
5. 原保留最近消息数、最新任务回复保护、工具完整性、分支/检查点比对、插入摘要不删除原历史等行为保留。
6. 压缩失败只显示“任务已完成，但自动压缩失败；原记录和任务结果均已保留”，不把成功任务改判失败，不因维护失败暂停消息队列。维护被取消时继续传播取消，但已经完成的回复先前已保存。
7. 状态显示“任务已完成，正在自动压缩上下文…”。设置页说明同步修改。

后置维护仍在同一生成 job/团队准入 permit 内串行进行，避免维护与下一条排队任务并发改会话；job 结束、队友等待完成事件以及准入释放仍在维护之后。它不是另起一个无主后台任务。当前成员耗时统计仍覆盖此 job 的模型/工具与压缩维护，不在本轮单独更改计时口径。

## 明确保留的限制

- 本轮**只调整压缩时机**，没有修改百分比或“真实 usage 与全量粗估取较大值”的计数规则。约 10%/15% 提前判阈值的独立问题仍见 `EARLY-TEAM-COMPRESSION-20261028.md`。
- 用户要求任务中不压缩，因此若一个任务在完成前超过模型硬窗口，请求仍可能失败；没有私自添加中途应急摘要来推翻该要求。
- 保留最近消息区中的巨型消息、无收益反复摘要等旧问题并未在本轮声称解决。
- `AutoCompressionState` 的旧 helper/测试尚在，但运行中的请求工厂已不再调用。
